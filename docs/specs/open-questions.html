問題 1TaiwanStockPER 完整資料期間 已解決

問題點（已釐清）

測試 22 查 TaiwanStockPER 時指定了 start_date=2024-01-01， 回 667 筆，因此記為「2024-01 起」。但當時不知道 start_date 是必填參數 —— 不帶會回 400，所以「無日期參數」這個測試從來沒成立過。

⚠️ 這正是「把查詢條件當成資料邊界」的陷阱。 我以為資料只到 2024，實際上是我自己把 start_date 設成 2024。

問題 2篩選條件全 AND 後剩幾檔未實算 高 · 待階段 2

問題點

⚠️ 實測過程中發現的連帶問題：align_score 沒有資料來源。
它依賴的維度 1／3／5 都還沒有客觀資料可算， 所以這個條件實際上根本沒辦法實作。

→ v1 實際可用的是三個條件，不是四個。 已從規格書 §2 的條件表移到 §11「v1 不實作」。

篩選條件是三個條件全 AND（§2）：

條件門檻篩掉什麼v1
ROE（多年平均）> 使用者設定（假設 12%）低 ROE 公司✅ 可實作
業外獲利比∈ [0.8, 1.2]業外損益過多或過少✅ 可實作
財務槓桿< 3.0高槓桿公司✅ 可實作
align_score< 8.0—❌ 無資料來源

我從沒算過 2000 檔跑完會剩幾檔。而「業外獲利比 ∈ [0.8, 1.2]」是個很窄的區間 —— 持有大額轉投資或金融資產的公司，業外損益 ÷ 稅前損益很容易超過 1.2。

直覺估計：ROE>12% 可能留下 600~800 檔，再交集 [0.8,1.2] 可能砍掉一半，槓桿<3 再砍一些 → 可能剩 100~300 檔。但這是猜的，沒有實算。

問題 3官方產業代碼 → 名稱字典 確認官方無

問題點 + 實測確認（測試 23.2）

我原本懷疑字典能從既有 API 回應反推，所以實測兩個端點的產業欄位到底裝什麼。

官方 API 給的是股票清單帶產業代碼，不是「代碼字典」：

來源產業欄位實際值distinct
TWSE t187ap03_L產業別 → 數字代碼（"01"、"28"）33 種
TPEx mopsfin_t187ap03_OSecuritiesIndustryCode → 數字代碼28 種
兩邊共用26 種重疊（同一套命名空間）
結論：兩個端點的產業欄位都只有數字代碼，沒有中文名稱欄位。 → 官方 open data 拿不到 code→name 字典，需另尋來源（TWSE 官網的產業別分類表）。

另兩個實測發現：

  • 出表日期已更新為 1151005（2026-10-05），比 decision-log §1.2 記載的 1151004 新一天 → 官方資料每日更新，測試結果有時效性
  • 官方 open data 回應格式與 FinMind 不同：直接是 JSON 陣列， 沒有 {status, data} 外層，解析不可套 FinMind 格式（本次第一次解析就因此失敗）

TPEx 另有可用欄位：Registration（KY 開曼群島 30 檔）、 ParValueOfCommonStock（多數面值 10 元）、 PreparationOfFinancialReportType（1=788／2=104）

問題 4創新板交易限制內容 已解決

原本的問題

§1 決策是「創新板股票納入系統，且篩選輸出時必須標註，因為其買賣規則與一般上市股不同」。 但「不同在哪」查不到，決策紀錄 §2.5 註明為未查證。

使用者決定

只需要標註是「創新版股票」就可以，差異在於買賣條件。

→ 不寫入任何具體法規內容。v1 的輸出只做標註， 「買賣條件有差異」這件事由使用者自己知道即可，系統不負責解釋。

這個決定解決了什麼

原本的擔心想清楚了：這題最容易被「順手寫個大概」誤過去。 決策紀錄已明確標為未查證，若介面先寫個猜的規則文案， 會變成沒有依據的權威陳述—— 這比不寫更糟。

使用者決定只標註，直接消除了這個風險：系統不對它沒查證的事下斷言。

問題 5token 與額度上限的關係 已解決

原本的問題

舊 spec 說免費方案是 600 次/小時，全量抓取要 1.6 天。 但實測發現多數 dataset 免 token 就能抓，且 20 次連續請求沒觸發 rate limit， 所以不知道免 token 的請求，額度上限到底是多少。

使用者的判斷：「無法知道，只能實際抓取試試看」—— 這個判斷是對的。

實測結果

# 60 次連續請求，不帶 token、不加 sleep、逐檔遞增 data_id
→ 60/60 成功，0 失敗，總耗時 12.0 秒
→ 平均每次 0.20 秒，實際約 5 requests/秒
這推翻了一整段舊設計。
項目舊 spec 假設實測
免費額度600 次/小時（0.167/秒）5 requests/秒
節流間隔每 7.2 秒一次可無節流
全量抓取耗時約 1.6 天約 40 分鐘
實測速率是舊 spec 預估的 30 倍。
額度端點再測結果：
端點結果
api.finmindtrade.com/api/v3/data404 {"detail":"Not Found"}
api.finmindtrade.com/api/v4/data200 success（正常取資料）
api.web.finmindtrade.com/api/v4/user_info404 404 page not found（純文字，非 API 錯誤）
⚠️ api.web.finmindtrade.com 沒有 /v4 路徑， 舊 spec §4.3 記載的 v2/user_info 是該網域唯一可能路徑。

⚠️ 但不能推論「沒有額度限制」

60 次不夠撞出每小時上限。不建議為了測上限去撞牆 —— 官方政策明載累積大量 4xx 請求會封鎖 IP 30 分鐘。

實務判斷：60 次無節流已足夠把抓取規劃從 1.6 天縮到數十分鐘， 額度真到上限時抓取途中會自然遇到（402），屆時再處理。 測試階段不追求撞出上限。

連帶修正：舊 spec 的一條錯誤設計紀錄

舊 spec §6.2 寫著「先前建議併發 5~10 是錯的，已收回」， 收回的理由是「瓶頸是帳號額度 0.167/秒，併發只會瞬間燒光當小時額度後吃 402」。

這個理由已被實測推翻 —— 免 token 時可跑 5 requests/秒。

但「不建議併發」的結論仍保留，理由改為避免瞬間吃 402， 並把節流間隔大幅放寬。改的是理由，不是結論。
