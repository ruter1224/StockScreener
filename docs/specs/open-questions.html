問題 1TaiwanStockPER 完整資料期間未確認 低

問題點

2026-10-06 測試 22 查 TaiwanStockPER 時指定了 start_date=2024-01-01，回 667 筆。我當時把它記為「2024-01 起」，但沒有測過不帶日期參數時的完整期間。

所以不清楚這個 dataset 是：

  • 只有 2024 年起（667 筆 ≈ 2.7 年）
  • 還是更早就有，只是我限定了範圍

對照參考：TaiwanStockPrice 有 11.7 年、TaiwanStockTradingDate 有 6,936 日。 若 PER 只有 2.7 年，明顯是後建的新 dataset。

問題 2篩選條件全 AND 後剩幾檔未實算 高

問題點

篩選條件是四個條件全 AND（§2）：

條件門檻篩掉什麼
ROE（多年平均）> 使用者設定（假設 12%）低 ROE 公司
業外獲利比∈ [0.8, 1.2]業外損益過多或過少
財務槓桿< 3.0高槓桿公司
align_score< 8.0無法計算（依賴外部資料）

我從沒算過 2000 檔跑完會剩幾檔。而「業外獲利比 ∈ [0.8, 1.2]」是個很窄的區間 —— 持有大額轉投資或金融資產的公司，業外損益 ÷ 稅前損益很容易超過 1.2。

直覺估計：ROE>12% 可能留下 600~800 檔，再交集 [0.8,1.2] 可能砍掉一半，槓桿<3 再砍一些 → 可能剩 100~300 檔。但這是猜的，沒有實算。

影響層面

模組影響
screening/最直接影響。條件的寬窄決定清單長度
scoring/影響工作量。若剩 500 檔，使用者要打 2500 次分數（5 維 × 500）→ 不可能定期做
產品契約若剩不到 30 檔，篩選條件過於嚴格，整個漏斗失去意義
valuation/無影響，只對入選股票計算
這是唯一可能讓架構需要重設計的問題。

回想 grill 第 1 題我說過的話：規模問題不靠砍功能解決。 如果實算後發現只剩 20 檔，該檢討的是篩選條件，不是把五維評分砍掉。

範圍

要動的檔案thresholds.yaml（調整門檻）
screening/（條件邏輯）
可能影響 spec §2
要不要重寫架構有可能

單條件通過數 → 逐步交集

實算方法（需要階段 2 的財務指標先算完）：

# 逐條件收窄，看每一步砍掉多少
n0 = 2000                      # 全部
n1 = n0[roe_5y > 12]              # ROE 篩
n2 = n1[non_op between 0.8, 1.2]   # 業外比
n3 = n2[leverage < 3]                # 槓桿
# 逐行印出 n1, n2, n3，看瓶頸在哪一條
⚠️ 另一個隱藏問題：align_score 目前無資料來源。 規格書 §2 把它列為篩選條件，但維度 1／3／5 都還沒有客觀資料可算， 這個條件實際上還沒法實作。實算時要先確認它的狀態。

問題 4創新板交易限制內容未查證 低

問題點

§1 決策是「創新板股票納入系統，且篩選輸出時必須標註，因為其買賣規則與一般上市股不同」。

但「不同在哪」我查證不到。決策紀錄 §2.5 註明： > ⚠️ 未查證：創新板的具體交易限制內容。spec 只寫 flag 機制，不寫法規細節。

這是刻意的選擇 —— 法規會變動，應獨立成文件並引用官方來源，不寫進 spec。

影響層面

模組影響
transform/無影響。is_innovation_board flag 機制已定案（§1.5，37 檔全在 TWSE）
screening/無影響。創新板不另設篩選條件
app/只影響提示文案。要標註，但標什麼字需要查證
使用者判斷不知道限制內容，使用者可能用一般上市股的習慣操作
影響可控的原因：flag 機制本身已完整（判準、覆蓋率、資料來源都確定了）， 缺的只是「顯示什麼字」。這是文案工作，不是架構工作。

問題 5token 與額度上限的關係未驗證 中

問題點

舊 spec 說免費方案是 600 次/小時，一天 14,400 次，所以全量抓取要 1.6 天。這個數字影響很大。

但實測發現兩件事：

  • 多數 dataset 免 token 就能抓（§6.1 全部清單）
  • 20 次連續請求沒觸發 rate limit（測試 21.2），實際限制比預期寬鬆
  • 無 token 無法查額度：/user_info v4 回 404、v2 回 200 但 body 是「請輸入 token」

所以不知道：免 token 的請求，額度上限是 600/小時，還是更低？

影響層面

模組影響
core/finmind_client.py速率控制參數。7.2 秒/次 是照 600/小時 算的，若上限更低要調慢
storage/sync_state.py抓取耗時估算 → 續跑點設計的實際價值
掛機時間1.6 天是規劃基礎，若變 3 天就要調整維護時段處理
token 管理若免 token 額度夠用，7 天過期問題完全消失，§4 整節可大幅簡化
雙向影響：
• 若免 token 就夠 → .env、token 倒數、換 token 流程全部不需要，架構更簡單
• 若免 token 不夠 → 必須用 token，7 天週期性更換，掛機抓取要中斷續跑

範圍

要動的檔案core/finmind_client.py 速率參數
spec §4（若免 token 夠用可整節刪）
要不要重寫架構通常不用
改參數即可，但 §4 可能整節不需要
解法用帶 token 的方式
打 /user_info 看實際額度

驗證方式：

# 有 token 時，回應會帶實際額度欄位
GET https://api.web.finmindtrade.com/v2/user_info
Authorization: Bearer {token}
→ { user_count, api_request_limit }

拿到 api_request_limit 的實際數值後，就能知道免費層的真實上限。 若需要 token 才能測，則取一個 token（免費自助，7 天有效）即可，不必付費。

⚠️ 成本很低但容易被跳過。這題只要一個免費 token 就能完全解決， 而且可能讓整個 token 管理機制消失。建議在階段 1 一開始就測掉。

建議處理順序

順序動作時機理由
1#5 實測 token 額度階段 1 開始前成本最低（一個免費 token），但可能簡化整個 §4 架構
2#1 測 PER 完整期間階段 1 抓取時順便不帶日期參數打一次就知
3#3 補產業代碼字典階段 2 前開始編輯 CAGR 對照表之前補上
4#2 實算篩選剩幾檔階段 2 財務指標算完後需要 ROE／業外比／槓桿都算得出來才能算
5#4 查創新板規則階段 4 介面只有文案需要，不急
結論：5 項中只有 #2 有實質架構風險，且必須等財務指標算完才能驗證（階段 2）。 其餘 4 項都是低成本可解的補充工作。沒有任何一項阻擋階段 0（專案骨架）。
